Design Rationale — Dashboard

  • Top-level status badge on the Device Summary card gives an immediate pass/warn/fail signal without requiring the user to scroll.
  • Per-camera cards use a consistent header+body+chip-row layout. The header badge mirrors the hardware level (FULL / LIMITED / LEGACY) so triage is instant.
  • Capability chips (RAW, ZSL, HDR) are colour-coded green/grey so supported features are visually distinct from unsupported ones.
  • Inline warning banners inside cards surface active errors at the point of context rather than requiring navigation to a separate error screen.
  • Bottom Navigation Bar (5 destinations) follows Material Design 3 guidance for primary navigation on phones. The active tab is indicated by a filled icon + indicator dot.
  • Tab chips in the App Bar sub-row allow quick filtering between Overview / Cameras / Errors without leaving the screen.

Design Rationale — Camera Detail

  • Hero row at the top surfaces the three most critical identifiers (Hardware Level, Facing, ID) in large type for immediate orientation.
  • Grouped sections (Sensor / Optics / 3A / Streams) mirror the logical groupings in CameraCharacteristics, reducing cognitive load for developers.
  • Status dots in the 3A section use the traffic-light convention (green = active/supported, amber = partial, red = unsupported) for rapid scanning.
  • Capability chips at the bottom use green fill for supported capabilities and grey for absent ones, avoiding the need to read every label.
  • Share icon (↑) in the App Bar enables exporting the full characteristics dump — a critical diagnostic workflow.
  • Back arrow replaces the hamburger menu since this is a detail screen, following Material Design navigation hierarchy rules.

Design Rationale — Live Preview

  • Preview-first layout: The viewfinder occupies the top ~40% of the screen so the user can verify the camera is functioning visually before reading metadata.
  • Overlay metadata bar at the bottom of the preview surface shows the most critical 3A states (AE/AF/AWB) and current ISO/exposure without requiring the user to scroll.
  • Collapsible metadata panel below the preview allows the user to expand or collapse detailed CaptureResult data, keeping the preview usable on small screens.
  • Progress bars for Exposure Level and Focus Distance provide an analogue representation of scalar values, which is faster to interpret than raw numbers alone.
  • Failure counter in Frame Statistics is a key diagnostic metric — a non-zero value immediately signals a problem.
  • Camera switch FAB (⇄) allows switching between cameras without leaving the preview screen, following the single-task focus principle.

Design Rationale — Error Log

  • Severity badge (ERROR / WARN / INFO) is the leftmost element in each card header so the user can scan severity before reading the message.
  • Filter chips at the top allow filtering by severity level or camera ID, reducing noise when diagnosing a specific camera.
  • Structured fields (Camera ID, Source callback, Error Code, Recovery state) mirror the structured telemetry recommended in the error handling best practices document.
  • Timestamp on each entry enables correlation with other system logs (e.g., adb logcat).
  • Recovery field on error entries communicates the current recovery state, helping the user understand whether the app is actively retrying.
  • Export icon (↑) in the App Bar allows sharing the full log as a text file for offline analysis.

Design Rationale — Capture Test

  • Validation chips below the stream configuration confirm that the combination is valid before the user runs the test, preventing a predictable onConfigureFailed.
  • Prominent CTA button uses the accent colour and full-width layout to make the primary action unmistakable.
  • Test history cards show the last N results so the user can identify intermittent failures (e.g., a single REASON_ERROR in an otherwise passing run).
  • Latency progress bar provides a visual benchmark — a bar near 100% would immediately flag a performance problem.
  • PARTIAL badge on Run #2 communicates that the session configured successfully but the capture itself failed, which is a different diagnostic path than a full failure.

Design Rationale — Settings

  • Toggle switches for boolean settings follow Material Design 3 conventions with a clear on/off visual state (blue = on, grey = off).
  • Secondary text under each setting label explains the effect, reducing the need for a separate help screen.
  • Grouped sections (Logging / Export / Background Monitoring) prevent the settings list from becoming an undifferentiated wall of options.
  • Background monitoring toggles are a critical diagnostic feature — they allow the app to track AvailabilityCallback events even when not actively using the camera.

Design Rationale — Fatal Error State

  • Red App Bar provides an unmistakable visual signal that the app is in a failed state, distinct from all other screens.
  • Error code + numeric code are both displayed so the screen is useful for both end-users and developers reading logs.
  • Recovery attempts counter communicates that the app has already tried to recover automatically, setting correct user expectations before they attempt a manual retry.
  • Two CTAs: a primary "Retry" action and a secondary "Export Error Report" action. The export action is critical for diagnostic apps — it allows the user to share the full error context with a developer.
  • Plain-language description below the error code explains what the error means in human terms, following the principle that error messages should be actionable and understandable.
